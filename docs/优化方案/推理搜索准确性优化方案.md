# Research Agent 推理搜索准确性优化方案

## 一、现状分析

### 1.1 测试结果
- **validation 验证集**: 10题中正确2题，准确率 **20%**
- **batch_run 测试集**: 约20+题，大量答案错误

### 1.2 根因分析（按影响程度排序）

#### 问题 P1：搜索基础设施严重不稳定（致命）
- **现象**: `batch_run.md` 中出现 **1023次** 搜索错误/超时
- **根因**: SearXNG 作为主搜索引擎频繁 `Connection timed out after 6004 milliseconds`
- **影响**: Agent 在关键推理链条上拿不到搜索结果，被迫靠猜测推理，导致整条推理链崩溃
- **代码位置**: `research_agent/search.py:882-908` — SearXNG 作为 primary provider，失败后 fallback 链不够健壮

#### 问题 P2：LLM 推理能力不足以支撑复杂多跳（核心）
- **现象**: Agent 使用 `qwen3-max`（`core.py:474`），temperature=0.4，max_tokens=1024
- **根因**:
  1. **max_tokens=1024 严重不足** — 复杂多跳推理需要长思维链，1024 tokens 经常在推理中途被截断
  2. **temperature=0.4 偏高** — 事实性推理任务应更低（0.1-0.2），减少幻觉
  3. **模型能力天花板** — qwen3-max 在复杂多跳推理上的能力有限，尤其是需要跨语言、跨领域关联的题目
- **日志证据**: 多个题目中 Agent 的推理过程被截断，无法完成完整的约束验证表

#### 问题 P3：Planner 生成的计划质量低且未被有效利用（重要）
- **现象**: `[Planner] Failed to generate plan: 'NoneType' object is not subscriptable` 频繁出现
- **根因**: `planner.py` 中 `max_tokens=512` 太小，JSON 输出经常被截断导致解析失败；即使成功生成，plan 只是被拼接到 system prompt 中，Agent 并不严格遵循
- **代码位置**: `research_agent/planner.py:133` — `max_tokens=512`

#### 问题 P4：搜索查询质量差 + 重复搜索（重要）
- **现象**: 日志中大量 `Query too complex, invoking LLM optimization`，优化后的查询仍然过长或不精准
- **根因**:
  1. Agent 倾向于生成过长的自然语言查询，而非精准关键词
  2. `_optimize_search_query` 用 LLM 优化查询，但优化效果不稳定（有时反而更差）
  3. 重复搜索检测阈值 `SequenceMatcher ratio > 0.95` 太高，大量语义重复的查询未被拦截
- **代码位置**: `research_agent/executor.py:38` — 相似度阈值

#### 问题 P5：答案合成和清洗环节丢失正确答案（中等）
- **现象**:
  1. `[Synthesizer] Error synthesizing answers: 'NoneType' object is not subscriptable` — 合成器崩溃
  2. 3个 Agent 中有1个给出正确答案，但合成器选了错误的
  3. `verify_and_clean_answer` 有时将正确答案"清洗"成错误答案（如翻译错误）
- **根因**:
  1. 合成器只截取 trace 最后 2000 字符（`answer_synthesis.py:103`），可能丢失关键推理证据
  2. 答案清洗的语言翻译逻辑有时错误翻译专有名词

#### 问题 P6：web_fetch 内容摘要丢失关键信息（中等）
- **现象**: `executor.py:75-88` 对超过 1000 字符的 web_fetch 结果进行 LLM 摘要，max_tokens=512
- **根因**: 摘要过程中丢失了关键的数字、日期、人名等精确信息，而这些恰恰是多跳推理的核心
- **影响**: Agent 基于不完整的摘要做推理，导致约束验证失败

#### 问题 P7：多 Agent 并行但缺乏多样性（低）
- **现象**: 3个 Agent 使用完全相同的 prompt、temperature、搜索策略
- **根因**: 没有引入搜索策略多样性（如不同语言、不同锚点），3个 Agent 经常走相同的错误路径

## 二、优化方案

### 方案 A：搜索基础设施加固（优先级：P0，预期提升：+15-20%）

#### A1. 搜索 Fallback 链重构
**改什么**: `research_agent/search.py` 的 `web_search` 函数
**怎么改**:
```
当前逻辑: SearXNG → (失败) → Serper/Baidu/DDG 并行
目标逻辑:
  1. SearXNG + Serper + DDG 三路并行发起（不等 SearXNG 超时）
  2. 设置 3 秒快速超时（当前 6 秒太长）
  3. 任一返回结果即可用，合并去重
  4. 增加 Google Scraper 作为第四路备选
```
**为什么**: 当前串行等待 SearXNG 超时浪费 6 秒，且失败后 fallback 链启动太晚

#### A2. SearXNG 超时降低 + 健康检查
**改什么**: SearXNG 调用处的超时配置
**怎么改**:
- 搜索超时从 6s 降到 3s
- 启动时做一次健康检查，如果 SearXNG 不可用则整个 session 跳过它
- 添加断路器模式：连续 3 次失败后 60 秒内不再尝试

#### A3. 搜索结果缓存
**改什么**: 新增搜索缓存层
**怎么改**: 对相同/高度相似的查询（SequenceMatcher > 0.85）直接返回缓存结果，避免重复网络请求

---

### 方案 B：LLM 调用参数优化（优先级：P0，预期提升：+10-15%）

#### B1. 增大 Agent 推理的 max_tokens
**改什么**: `research_agent/core.py:479`
**怎么改**: `max_tokens: 1024 → 4096`
**为什么**: 复杂多跳推理需要长思维链。1024 tokens 经常在约束验证表完成前被截断，导致 Agent 无法输出完整的 Final Answer

#### B2. 降低 temperature
**改什么**: `research_agent/core.py:478`
**怎么改**: `temperature: 0.4 → 0.15`
**为什么**: 事实性推理任务需要确定性输出，0.4 的随机性导致 Agent 在关键推理节点产生幻觉

#### B3. 增大 Planner 的 max_tokens
**改什么**: `research_agent/planner.py:133`
**怎么改**: `max_tokens: 512 → 1024`
**为什么**: 当前 512 tokens 导致 JSON plan 频繁被截断，解析失败

#### B4. 增大 web_fetch 摘要的 max_tokens
**改什么**: `research_agent/executor.py:84`
**怎么改**: `max_tokens: 512 → 1024`，并在摘要 prompt 中强调"必须保留所有数字、日期、人名、地名"

---

### 方案 C：推理策略优化（优先级：P1，预期提升：+10-15%）

#### C1. 搜索查询生成优化
**改什么**: Agent 的 system prompt 中关于搜索查询的指导
**怎么改**:
```
在 MULTI_HOP_SYSTEM_PROMPT 的搜索执行阶段添加：
<search_query_rules>
1. 每次搜索查询不超过 6 个关键词
2. 优先使用英文搜索（信息覆盖面更广），中文实体用中文搜索
3. 使用引号包裹精确短语，如 "Tomáš Masaryk" "Prague Castle"
4. 禁止在查询中使用完整句子
5. 每次搜索后评估结果质量，如果前3条结果不相关，立即换关键词
</search_query_rules>
```

#### C2. 强制分步验证 + 早停机制
**改什么**: `research_agent/core.py` 的 agent_node 中 Final Answer 检测逻辑
**怎么改**:
- 当前逻辑在检测到 Final Answer 但没有验证表时会强制要求补充，但这个检查只看 `"CONSTRAINT VERIFICATION TABLE"` 字符串，太死板
- 改为：检测 Final Answer 时，检查 content_buffer 中是否包含至少 3 个 `✓` 标记，如果不够则拒绝并要求补充验证

#### C3. 重复搜索拦截阈值调整
**改什么**: `research_agent/executor.py:38`
**怎么改**: `SequenceMatcher ratio: 0.95 → 0.80`
**为什么**: 当前阈值太高，Agent 经常用略微不同的措辞搜索相同内容，浪费步数

#### C4. 动态步数分配
**改什么**: `research_agent/core.py` 的 urgency 逻辑
**怎么改**:
- 当前固定 30 步，最后 5 步进入 urgency mode
- 改为：如果 Agent 在前 15 步内已找到高置信度答案（trace 中包含 ≥3 个 ✓），允许提前结束
- 如果 20 步后仍无候选答案，自动切换到"宽泛搜索"模式

---

### 方案 D：多 Agent 多样性增强（优先级：P1，预期提升：+5-10%）

#### D1. 差异化搜索策略
**改什么**: `agent.py` 和 `run_batch.py` 中的多 Agent 启动逻辑
**怎么改**:
```
Agent 1: 标准策略（英文优先搜索）
Agent 2: 中文优先搜索 + 不同锚点选择提示
Agent 3: 反向推理策略（从答案类型反推搜索方向）
```
通过在每个 Agent 的 messages 中注入不同的策略提示实现

#### D2. 答案合成器增强
**改什么**: `research_agent/answer_synthesis.py:103`
**怎么改**:
- trace 截取从 2000 字符增加到 4000 字符
- 在合成 prompt 中增加"如果某个 Agent 的 trace 中包含更多已验证约束（✓标记），优先采信该 Agent"
- 添加异常处理，避免 `'NoneType' object is not subscriptable` 崩溃

---

### 方案 E：答案后处理优化（优先级：P2，预期提升：+3-5%）

#### E1. 答案清洗保守化
**改什么**: `research_agent/answer_synthesis.py` 的 `verify_and_clean_answer`
**怎么改**:
- 对专有名词（人名、地名、机构名）不做翻译，保留原文
- 只在答案明显是解释性文字时才清洗
- 添加"如果原始答案已经是简洁的实体名/数字/年份，直接返回不做处理"的短路逻辑

#### E2. Final Answer 提取逻辑加固
**改什么**: 答案提取的正则匹配
**怎么改**: 在 LLM 清洗之前，先用正则提取最后一个 `Final Answer:` 后的内容，如果提取结果是简洁的实体名（<50字符），直接使用，跳过 LLM 清洗

---

## 三、实施优先级与预期效果

| 阶段 | 方案 | 改动范围 | 预期提升 | 风险 |
|------|------|----------|----------|------|
| 第一阶段 | B1+B2+B3 (参数调优) | 3行代码 | +10-15% | 极低，纯参数调整 |
| 第一阶段 | A1+A2 (搜索加固) | search.py | +15-20% | 低，需测试 fallback 链 |
| 第二阶段 | C1+C3 (查询优化) | prompt + executor | +5-10% | 低 |
| 第二阶段 | B4+E1+E2 (后处理) | executor + synthesis | +3-5% | 低 |
| 第三阶段 | C2+C4 (推理策略) | core.py | +5-10% | 中，需充分测试 |
| 第三阶段 | D1+D2 (多样性) | agent.py + synthesis | +5-10% | 中 |

**保守估计**: 全部实施后准确率从 20% 提升到 **45-55%**
**乐观估计**: 如果搜索基础设施稳定 + 参数调优到位，可达 **55-65%**

## 四、关键风险提示

1. **搜索基础设施是最大瓶颈**: 如果 SearXNG 持续不稳定，其他所有优化效果都会大打折扣。建议优先确保至少有 2 个稳定的搜索 provider
2. **模型能力天花板**: qwen3-max 在极复杂的多跳推理上可能存在能力上限，如果优化后准确率仍不理想，需考虑换用更强的模型（如 qwen3-235b 或 deepseek-r1）
3. **max_tokens 增大会增加成本和延迟**: 4096 tokens 的推理输出会使单次 LLM 调用时间和费用翻倍，需权衡
4. **多 Agent 并行的成本**: 3 个 Agent 并行意味着 3 倍的 API 调用成本，如果预算有限可考虑降为单 Agent + 更强模型
